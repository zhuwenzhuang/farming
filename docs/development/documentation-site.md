# Public Documentation Site

> Chinese version: [documentation-site.zh_cn.md](./documentation-site.zh_cn.md)

The public documentation site is a standalone VitePress project under
`docs-site/`. Its dependencies, lockfile, build commands, and CI workflow are
separate from the Farming application. Durable architecture and maintainer
contracts remain under `docs/`.

## Content Boundary

The public site contains task-oriented user documentation for behavior that is
ready to explain and support. Draft-only surfaces stay out of the site.
Implemented capabilities that still lack representative real-world cases may
be documented only in the experimental section and must carry a visible
experimental notice.

The site publishes mirrored Chinese and English user documentation. Chinese
pages live under `docs-site/cn/`, English pages under `docs-site/en/`, and the
locale switch remains available in both languages. A user-facing content
change updates both versions in the same commit unless it is explicitly
language-specific.

## Presentation Contract

The site is a documentation entry point, not a product marketing page. Keep the
homepage concise and task-oriented: a short user-facing introduction, the Code
and CRT entry points, then common capabilities, plugins, and workflows. Keep
operational product screenshots on the pages that explain those interfaces;
the homepage hero may use restrained theme-specific brand artwork. Code and CRT
are the two primary interfaces. Browser and other optional capabilities belong
under plugins or experimental features and must not be presented as equivalent
top-level products.

Use the warm Farming visual identity lightly in the hero while keeping reading
surfaces quiet and high-contrast. Prefer system fonts, stable layouts, modest
cards, and direct user language. Avoid invented slogans, oversized promotional
sections, customer-proof patterns, or repeated feature inventories. Screenshots
should explain a specific workflow or interface; they are evidence, not a
substitute for documentation.

## Local Commands

```bash
cd docs-site
npm ci
npm run dev
npm run build
npm run preview
```

`npm run build` is the authoritative link and static-build check. Product
screenshots shared by both locales live under `docs-site/public/cn/assets/`; keep
them anonymous and free of private hosts, tokens, and draft-only UI.

Regenerate product screenshots from the repository root:

```bash
npm run docs:product:screenshots
```

Capture selected dark-appearance variants without replacing the light files:

```bash
FARMING_SCREENSHOT_APPEARANCE=dark \
FARMING_SCREENSHOT_FILES=05-mobile-agent-chat.png,11-code-agent-process.png \
npm run docs:product:screenshots
```

This command captures the real built Farming UI with anonymous, deterministic
workspaces and Agent fixtures. It updates the canonical product screenshots and
synchronizes the public-site selections into `docs-site/public/cn/assets/`. Do not
replace these captures with manually composed mockups. Dark captures use a
`-dark` filename suffix; screenshots whose product surface is already natively
dark, such as Usage activity and Farming CRT, keep their canonical filename.

The Farming Browser plugin and Viewer screenshots are generated by the focused
Browser E2E scenarios. They still capture the real UI, but the main screenshot
command does not synchronize them yet. When updating those images, run the
corresponding Browser E2E screenshot flow and verify the public-site references.

Do not add documentation-site dependencies to the root `package.json`, use an
npm workspace, or make the Farming application build depend on this project.

## Publishing

`.github/workflows/docs.yml` builds the site from `main` and deploys the static
artifact to GitHub Pages. The repository Pages source must be set to GitHub
Actions. The default project-site base path is `/farming/`; a future custom
domain can override it through `FARMING_DOCS_BASE`.
The canonical origin and sitemap host can be changed through
`FARMING_DOCS_ORIGIN`.
