# ACP Backend Runtime

> Chinese version: [acp-runtime.zh_cn.md](./acp-runtime.zh_cn.md)

Farming has an Agent Client Protocol runtime for Codex, Claude Code, OpenCode, and Qoder. Backend lifecycle and frontend presentation remain intentionally separate: the backend owns the Agent process, ACP session lifecycle, normalized state, and control APIs, while `src/components/code/acp/` owns ACP-only Chat behavior.

## Provider Connections

- Codex uses the pinned `@agentclientprotocol/codex-acp` adapter. A version-locked `patch-package` delta adds the negotiated `_codex/session/steer` extension with `turn/steer` forwarding, plus standard ACP `session/fork` backed by Codex `thread/fork`. Packaging fails if the pinned upstream package no longer matches the reviewed patch, then copies the exact patched adapter into the release under a locked SHA-256. Development and build refreshes verify a temporary copy and atomically replace the target entry, so they cannot truncate a live adapter. Installed packages launch that immutable artifact and never rely on post-install mutation. Standalone CLI builds bundle it behind an internal process entry and must complete an ACP `initialize` handshake as part of native artifact smoke.
- Claude Code uses the pinned `@agentclientprotocol/claude-agent-acp` adapter.
- Bundled ACP adapters launch the Farming-owned provider runtime selected for
  ACP. They do not reuse the system executable selected for a native Terminal;
  this separation is required for deterministic protocol behavior and safe
  Chat/Terminal session switching.
- OpenCode uses its native `opencode acp --cwd <workspace>` command.
- Qoder uses its native `qodercli --acp` command. Qoder can emit the tail of a loaded history after `session/load` returns, so Farming waits for the replay stream to settle before exposing the restored session.
- All four communicate through the official `@agentclientprotocol/sdk` over newline-delimited JSON-RPC on subprocess stdio.

Adapter package versions are exact production dependencies. Farming does not run `npx latest` during Agent startup.

ACP adapter and provider-runtime pins should be refreshed toward the latest
compatible release. A refresh is accepted only after the reviewed patch and
integrity contract, ACP initialization, session load/resume, and Chat/Terminal
switching pass; keeping a materially stale ACP runtime is a compatibility bug,
not a reason to make Terminal use the same stale executable.

## Process Sharing And Hibernation

Farming shares stateless capabilities before it shares stateful Agent runtimes. Browser and Computer are projected into ACP sessions as shared Streamable HTTP MCP endpoints rather than one stdio MCP subprocess per Agent. Each projection receives an unguessable bearer token bound to the exact Agent, capability, and canonical launch workspace. The Agent record retains that stable capability workspace for the lifetime of the projected runtime, so a later asynchronous Git-worktree display update cannot invalidate the token. The endpoint revalidates the current ACP binding through an O(1) authoritative Agent lookup on every request, and only the backend exchanges that scoped identity for Farming control authentication. A Browser token cannot call Computer, a deleted or detached Agent cannot keep using its token, symlink and real workspace paths resolve to the same identity, and user-provided MCP definitions remain independent session inputs.

Farming has no default live-Agent count cap and never hibernates an ACP runtime merely because any fixed number of Agents coexist. Heartbeat cleanup and cold recovery do not perform count-based eviction. Generic zombie cleanup also excludes active ACP lifecycle states, so a stale activity timestamp cannot interrupt a working, waiting, connecting, reconnecting, interrupting, or hibernating Agent. Logical Agent inventory and live process capacity are separate concerns; a small local constant must not become product semantics. A Worker may request reclaim only after an authoritative resource-pressure signal and must name the exact candidate. AgentManager does not remember or queue that request for a working Agent: only a currently idle, non-main, unpinned ACP runtime is admitted, and the runtime rechecks that there is no active Turn, session or configuration mutation, deferred configuration, permission, elicitation, patch decision, child Session, or client terminal. Farming then writes an exact checkpoint, closes the connection, and proves that the exact adapter process group exited before clearing its persisted identity. An uncertain exit becomes an explicit error and retains the identity for exact cleanup; it is never treated as successful hibernation. The persisted `hibernated` state remains a durable exit proof. Cold Server recovery restores its logical Agent row, request scope, and retained checkpoint without starting a provider process; the same provider Session wakes through authoritative `session/load` only when a later user action requires provider work.

Transcript and tool-detail reads use the retained reducer and do not wake a hibernated Agent. A new prompt or a provider mutation such as list, fork, authentication, close, mode, or configuration change first joins any in-progress hibernation for that Agent, then moves it through `reconnecting`, starts a fresh isolated process, and performs authoritative `session/load` for the same provider Session, workspace, Agent Home, additional directories, and MCP scope. The transcript revision fence cannot move backwards. Wake failure is visible and the user mutation is not replayed. If exact process cleanup succeeded, the failed binding retains a structured retry admission so the next explicit action may retry the same load; retryability is not inferred from provider error text.

Farming does not yet multiplex unrelated Agent Sessions inside one provider process. ACP has no universal session-scoped environment and identity channel for Farming ownership variables, provider homes, custom MCP configuration, permissions, and child-session routing. OpenCode's directory-keyed instance cache is useful prior art but is not a sufficient isolation proof. A future shared Runtime Host must be enabled by provider-adapter capability declarations and must prove session-scoped workspace, environment, MCP, permissions, exact recovery, and bounded capacity; providers without that proof remain one process per live Agent and still benefit from shared capabilities and hibernation.

## Session Semantics

A live Codex adapter may advertise the versioned `_codex/session/steer` extension in addition to standard ACP capabilities. Farming enables it only from the initialize response and never from the provider name alone.

The runtime supports ACP `initialize`, `authenticate`, `logout`, `session/new`, `session/load`, `session/resume`, `session/list`, `session/fork`, `session/delete`, `session/close`, `session/set_mode`, `session/set_config_option`, `session/prompt`, and `session/cancel` when the Agent advertises the corresponding capability. New, load, resume, fork, and list requests preserve standard additional-directory scope; new, load, resume, and fork also preserve client-provided command or HTTP MCP server definitions at the adapter boundary. The unified WebSocket and control-HTTP Agent start interfaces accept those two standard session inputs, and a Chat/Terminal or permission restart carries them into the replacement ACP binding. The inputs are kept out of browser-facing Agent state and stored only in the private `0600` Farming session record so crash recovery can reconnect the same scope. Farming does not invent support for an unadvertised optional method.

ACP configuration has two distinct authorities. A Session with no user override accepts the configuration returned by `session/new` or `session/load`, so a new Agent continues to inherit its selected Agent Home's on-disk defaults. After a user configuration mutation is accepted and confirmed, Farming records the generic `configId`/value override in that same private Session record and keeps it in the live binding restart options; a deferred mutation becomes durable only after its post-Turn flush is confirmed. Process reconnect, hibernation wake, cold Server recovery, permission restart, and Chat/Terminal replacement load the authoritative provider Session first and then replay only those explicit overrides. Provider defaults are never copied into override metadata merely because the UI observed them. Replay processes a model override first when the live option identifies it, then revalidates every remaining exact `configId` and value against the refreshed `configOptions`; Farming never maps an override by its display label. A missing option, changed type, or removed select value is a deterministic incompatibility: Farming drops that override, keeps the provider's current value, persists the cleaned override set, and exposes a Session recovery warning without failing startup. A transport or provider mutation failure is not proof of permanent incompatibility, so Farming keeps that override for the next explicit runtime-recovery boundary, does not retry it again during the same recovery, and exposes one binding-scoped warning while the Session remains usable. The resulting confirmed `configOptions.currentValue` remains the sole browser projection, including boolean options such as Fast; the reducer checkpoint carries a display snapshot and revision fence but is not the durable override authority.

Conversation Fork support has one provider-adapter contract across Terminal and ACP. Each runtime declaration identifies whether Fork is supported, whether the source session or the target process materializes the child identity, which worktree modes are valid, and whether a live negotiated runtime capability is also required. Backend admission, browser actions, History Fork, and provider-specific execution all consume that contract; compatibility booleans are derived from it rather than maintained as a second capability list. The generic lifecycle therefore owns validation, identity, persistence, and recovery, while an adapter specializes only the provider operation. A target-process strategy includes Terminal CLI Fork and providers such as Claude ACP whose child must be created inside its owning adapter process. A source-session strategy creates the distinct provider session first and then loads it into the child runtime. Plain shells remain eligible for Agent/worktree duplication but do not claim Conversation Fork support.

For ACP, the browser exposes Conversation Fork only from a stable idle, recoverable error, or hibernated source whose last negotiated runtime capability advertised `session/fork`. Backend admission remains authoritative: it wakes error or hibernated sources through the normal reconnect path, rejects working or connecting sources without interrupting them, and rechecks the freshly negotiated capability before calling the provider. Resource-pressure reclamation therefore cannot bypass Fork safety, and a stale browser projection cannot manufacture support.

When a live idle ACP binding advertises `session/fork`, the Fork action below the latest completed Chat answer fences the exact transcript revision and creates a distinct provider session in a new ACP Chat Agent in the same workspace. Most adapters fork from the source binding and let the new Agent load the returned session. Claude's fork exists only in the adapter process that creates it until the child completes its first prompt, so Farming instead starts the isolated child adapter, loads the fenced source there, forks in that same process, closes its temporary source session, and keeps the returned child live on that process. The exact source binding checkpoint—including bounded child transcripts and committed patch decisions—crosses this transition only as private in-memory startup state and is installed under the returned child identity after the provider fork succeeds; returned child mode, configuration, and command state then override the source values. This keeps the child UI and tool details on the clicked revision even when provider history replay lags. A child Agent whose persisted parent and provider-fork identities are both present renders a presentation-only `Forked from agent` divider above its Chat transcript; the divider is not inserted into the ACP entry stream. A process loss before the first child prompt fails visibly instead of silently creating a different fork; after the first prompt, normal `session/load` recovery applies. Startup rollback stops the child process before asking the still-live source binding to delete the exact fork identity. If that provider deletion fails, the failure returns the exact retained identity for operator cleanup. This action does not launch a Terminal or infer support from browser-side provider lists. All Fork entry points preserve the source runtime: ACP Chat uses the fenced same-worktree conversation fork, while Terminal uses the provider-CLI fork paths. ACP Chat does not expose the new-worktree fork because that path is not supported.

The initialized client advertises the ACP file-system, terminal, terminal-authentication, boolean configuration, plan, form-elicitation, URL-elicitation, and terminal-output capabilities that Farming actually implements. Corresponding Agent requests are served by bounded workspace file access, managed client terminals, explicit permission cards, authentication UI, and elicitation forms. Elicitations without a `sessionId` remain request-scoped, including authentication-time requests before a session exists; session- and child-session-scoped requests keep their own origin. Session updates—including text, reasoning, plans, tool calls, diffs, terminals, resource links, images, audio, usage, commands, configuration, and child-session metadata—reduce into the same ordered session model. Protocol features are enabled from the live initialize/session responses, not from provider-name guesses.

Chat preserves these typed ACP parts instead of inferring them from assistant prose. Markdown remains a typed text part; its explicit file links and qualified inline-code references reuse the terminal's bounded file-location grammar, then pass through workspace/global-file normalization before opening. Tool-call `locations` remain bounded structured path/range records and render as workspace file anchors; they are never flattened into a `Locations` prose section and parsed back. HTTP(S) resource links remain external links, while local `file://` and workspace resource links open through the same workspace boundary. Images, audio, resources, tool calls, patches, plans, terminals, and collaboration metadata continue through their structured renderers rather than a competing text recognizer.

Codex may also emit host-only display directives inside an assistant text item. These are not public App Server item types or portable ACP content. Farming normalizes the supported `codex-inline-vis` directive at the provider boundary: only a lowercase `.html` basename in the exact current-thread directory under the selected Agent Home's `CODEX_HOME/visualizations/YYYY/MM/DD/<thread-id>` may become a standard ACP `resource_link`. The resolver canonicalizes the visualization root, thread directory, and file, rejects path or symlink escape, non-UTF-8 and files larger than 2 MiB, preserves directive literals inside fenced or indented Markdown code, and hides an incomplete streaming directive until it completes. The private syntax is removed from ordinary Markdown. Only the Farming-reserved presentation metadata attached by this normalization boundary authorizes a `text/html` result resource to render inline in Chat; another ACP resource with the same MIME type remains an ordinary resource. The inline viewer has no same-origin capability, permits the script/eval/WASM/blob features and bounded CDN set required by the Codex visualization runtime, and blocks remote connections, forms, nested frames, and object embedding. Missing, malformed, or invalid targets remain an explicit unavailable resource and are never guessed. Known Codex App Git and code-comment directives remain hidden transport hints; Farming does not execute their mutations. Final-answer resources, images, and audio are promoted to the result surface just like final-answer text instead of being stranded inside Process.

An existing history session keeps a Farming-owned reducer checkpoint under the config directory. Its identity includes provider, Agent Home, provider session id, and workspace; writes are compressed, file-and-directory synced, and atomically replaced. The checkpoint carries the primary reducer, child reducers, patch-decision fences, and the previous browser revision. Before a prompt Farming durably marks it dirty. ACP currently exposes neither a provider-owned opaque revision nor a conditional `session/resume`, so a timestamp comparison cannot prove that local state is exact. Farming therefore fails closed to `session/load`; the checkpoint is not accepted as the whole recovered state, but preserves the revision/reset fence so a browser cannot retain entries from a discarded reducer. When Qoder replays the authoritative message order and text but omits media blocks that were present live, Farming may restore only image or audio blocks from the same checkpoint user-message ordinal whose replayed text matches exactly; it never restores missing messages or replaces provider text. Bare resume and uncertain prompt failures remain dirty and can never create an exact recovery checkpoint. Local resume without replay may be enabled only if a future provider exposes a workspace-bound freshness token and a conditional-resume proof.

This distinction matters because ACP load replays the complete conversation through `session/update` notifications before the load request returns, while resume restores context without returning old messages. Farming registers the session reducer before sending load so early replay notifications cannot be lost. Replay updates reduce into the ordered stream without broadcasting one browser invalidation per entry; clients receive one settled snapshot after restoration. A reader whose `sinceRevision` is ahead of the rebuilt reducer, or at/before its reset fence, receives a full replacement rather than an empty delta.

History-origin Chat keeps a stable syncing surface until its first settled page arrives. The existing transcript endpoint returns a versioned checkpoint/delta envelope containing the exact Agent, provider Session, runtime epoch, source revision, target revision, replacement flag, and replay-settled proof. A browser installs a checkpoint, applies a delta only when its epoch matches and `fromRevision` equals the locally installed revision, and requests a replacement checkpoint after any gap or identity change. A late request for another Agent or an older revision cannot take over the visible view. The backend treats the revisioned reducer and checkpoint as authoritative and prepares a derived 20-turn presentation only after an idle Session has remained quiet. A newer revision cancels the quiet window, and a prepared result is published only after its runtime epoch, Session identity, and revision pass a final compare-and-swap check. Preparation is single-flight per Session, globally bounded, and stored in a byte-bounded LRU; eviction, restart, or preparation failure falls back to the same authoritative on-demand projection. Selecting an Agent switches to its Chat shell immediately. An exact settled prepared or on-demand checkpoint becomes visible in the same React commit without a fixed quiet timer. An unsettled history replay remains behind one stable syncing surface until the backend proves a settled checkpoint. After that first visible commit, continuous live deltas remain streaming.

The page status distinguishes locally loaded History rows from the backend's total discovered provider sessions. Scrolling near the bottom of the project list loads the next page; project-level “Show more” still controls only local presentation within the pages already loaded. Agent Search queries that full backend window instead of filtering only the pages already loaded in the browser. Matching is case-insensitive and covers visible Agent or session titles, Project names and paths, and exact or partial Resume IDs; provider metadata and transcript content are not searched. Backend-returned session identities are authoritative search matches so the scope can expand without being discarded by a second frontend title filter. History resume resolves provider metadata across the full backend window so an older session keeps its original workspace when it moves between Terminal and Chat. Claude and Qoder discovery treat only project-level transcript files as sessions; nested child-agent transcripts inherit the parent identity and remain replay details rather than duplicate History rows. Each provider-session row shows a compact Resume ID, with the complete identifier available on hover, so equal titles remain distinguishable without changing the resume identity passed to the backend.

Temporary Terminal provider identities do not poll or scan History. The backend owns their promotion to confirmed identities; that transition triggers one frontend refresh. The browser coalesces overlapping first-page reads of the same size, and concurrent backend inventory readers share one authoritative filesystem pass, so explicit initial hydration, History, and multiple browsers cannot multiply the same user-requested scan.

Opening History is a current-state boundary. Farming clears the previous provider Session list and shows Loading until the new request succeeds; failure remains visible and never falls back to rows from an earlier visit. History search follows the same contract.

ACP updates are retained in bounded, size-limited diagnostic form and reduced into one provider-neutral ordered entry stream. History replay and live updates use the same reducer. Adjacent compatible message chunks merge by message id, while Codex phase metadata remains attached and prevents commentary from merging across a `final_answer` boundary. A Codex steer message remains inside its owning root user turn and never becomes a transcript-slice turn boundary. Tool updates mutate the original tool-call entry by id, and plan entries update in place. Session metadata such as usage, modes, commands, and config options stays outside the conversation stream. Runtime notifications carry only lightweight invalidation metadata: live transcript revisions use the coalesced per-Agent `acp-session-revision` browser message instead of broadcasting the full workspace state, while initial hydration and reconnect still receive the authoritative full state. Transcript reads use a monotonic revision and replace only the affected entry suffix. The transcript page carries a compact ordered tool envelope with bounded inline detail, patch statistics, media references, and terminal ids; exact raw input/output and patches remain in the backend checkpoint and load through the tool-detail endpoint. A new reader explicitly negotiates `external-v1` transcript media so rolling upgrades leave old readers on inline media; negotiated media URLs use immutable content hashes rather than mutable array indexes and fail closed if that exact content is no longer authoritative. Only transport failures of the read-only transcript GET receive bounded automatic retries; view replacement cancels them, and prompt, terminal input, and every other write path remain outside this retry behavior.

## Farming Code Presentation

When negotiated, Codex input submitted during an active turn is sent as steer and remains inside that turn at its ordered transcript position, including native media blocks. A small, subdued `Steer` text marker sits below the bubble at the left so it remains distinguishable from the root prompt without competing with the conversation. Providers without the extension keep the visible queued-follow-up presentation.

The latest working ACP turn renders one subdued live-activity row at the bottom of its content for Codex, Claude Code, OpenCode, and Qoder. Its label and icon come only from provider-neutral typed ACP state such as thought, plan, and tool-call kind. Active tools and plan steps take precedence; otherwise Farming may use the latest bounded, visible Markdown bold heading from an ACP thought before falling back to a generic typed label. Unknown work uses a neutral loading indicator rather than a provider or plugin icon. The row is hidden while the session is waiting for permission or user input, or is interrupting, because those states have their own explicit interaction surfaces. Completed process summaries and historical actions remain text-only.

Short Chat transcripts start at the top of the reading surface instead of being pushed against the bottom Composer. Long histories still follow the latest content while the reader remains at the tail, preserve an explicit earlier reading position, and expose the jump-to-latest control when detached. Only an explicit reader scroll or text-selection gesture detaches follow-latest; transcript rendering and other late content-height changes keep the viewport attached to the tail. A detached Chat asynchronously checkpoints the first visible stable Turn or process-item identity plus its fractional viewport offset under the Agent's restart lineage. That browser-local anchor survives a Farming or page restart. Restore waits for the settled transcript reveal, loads older 20-turn pages while the anchor is outside the initial window, and falls back to the current tail only when the bounded authoritative history proves the anchor no longer exists. Late transcript updates never reapply an already-restored anchor, and a failed storage read or write cannot block Agent switching.

Farming Code separates the logical opened-Agent list from heavyweight browser views. Retained Agent shells and pooled xterm instances still use the bounded Agent-view working set, but a full Chat transcript tree exists only for the currently visible Chat. Switching Agents, opening Search or History, or entering the file editor first checkpoints the semantic reading anchor and then unmounts the inactive transcript, Markdown, disclosure, media, and Process state. Returning to that Chat reads the same authoritative backend checkpoint path and restores the saved Turn/process-item fractional anchor; disclosure state intentionally starts collapsed. This keeps frontend Chat memory proportional to the number of visible Chats rather than the number previously visited, without stopping or hibernating any backend ACP runtime.

When collaboration details are folded, the top-level child Agents use compact inline buttons and wrap only when the Turn runs out of horizontal space. Selecting one expands that Agent to the full bounded detail width in place; nested children remain inside that expanded parent.

ACP uses its own composer, draft namespace, permission cards, session controls, dynamic command menu, and transcript adapter under `src/components/code/acp/`. Terminal continues to use `CodeComposer` and the PTY input path without ACP branches. ACP client terminals use an embedded xterm view for real keystrokes, selection, output, resize, and stop behavior; this component is not shared with the Terminal page.

Every non-main ACP coding Agent receives the same Farming bootstrap and a runtime-scoped title token. Once it understands the task, the Agent submits a concise adaptive title through `farming title`; this path is provider-neutral across Codex, Claude Code, OpenCode, Qoder, and Qwen. Farming publishes the accepted title as a coalesced Agent-scoped delta, then acknowledges the command only after the latest title for that Agent is durable in private `adaptiveTitle` metadata. Concurrent startup updates therefore neither rebuild nor broadcast the full Agent inventory, and repeated titles for one Agent persist only the last value. A persistence failure explicitly rejects the command and restores the last durable fallback. Titles render in this order: user rename, adaptive Agent title, Provider Session title, runtime Session title, then Agent kind. A runtime restart rotates the token, so a late update from the replaced process is rejected. Title failure leaves the existing fallback visible and never blocks the prompt.

For a new Codex Session, the pinned adapter still publishes the first non-empty text prompt as an immediate fallback before the first Turn completes. A later explicit Provider thread name can replace that fallback until the Agent publishes its adaptive title. Farming records whether a custom title was user-specified in `titleUserSpecified`; a non-empty user title remains authoritative across adaptive or Provider updates and restart.

User, process, and result images share one click-to-enlarge viewer that closes from its close control, backdrop, or Escape without changing transcript state.

The composer renders the modes, model, reasoning level, boolean options, usage, and available commands negotiated from the live ACP session. The existing Chat UI design is preserved: an adapter projects the canonical ordered entries into its user/result/process view model without changing the composer or transcript component hierarchy. A Codex message marked with `final_answer` is the authoritative visible result even if history replay later emits a reasoning entry; providers without an equivalent marker retain the compatible tail heuristic. Earlier commentary, thoughts, tools, and plans stay inside the existing reversible process disclosure. During an active turn, that disclosure stays collapsed by default but presents a compact tool trail: at most four individual non-failed actions remain visible, earlier actions collapse into a count, intermediate failures stay off the default reading surface, each visible tool keeps its own reversible detail disclosure, and the latest non-empty commentary becomes a bounded plain-text progress preview. Rendering the preview as text, rather than clipping rich Markdown, ensures hidden links cannot remain in the keyboard focus order; the complete Markdown stays available in Process. Reasoning, older commentary, and failed-tool evidence remain available only through the complete Process disclosure instead of accumulating on the default reading surface. Codex collaboration and subagent-activity metadata stay in the bounded tool envelope and project into the Process area of the exact parent Turn that contains those ordered entries. Each child Agent remains directly discoverable as one collapsed card even while the rest of Process is folded; its primary label is the task and its secondary label is the authoritative Codex identity. Missing ancestors may be included to preserve the real thread hierarchy, but a latest snapshot alone never assigns an eventless descendant to an older Turn because it does not prove that descendant's birth Turn. Expanding a card reveals its ordered lifecycle milestones, coalescing only consecutive equivalent updates; selecting a milestone reveals the exact ordered parent-tool evidence inside that same Turn. This projection does not invent a writable peer chat when the adapter has not provided an independent ACP child Session. Formal ACP child Sessions continue to use their nested transcript, focused dialog, and independent Stop control. A running terminal tool auto-expands only after a 500 ms grace period and only after Farming observes real output; fast commands and newly reported failures stay collapsed, while a terminal already opened for live output remains open if it fails. Its expanded view owns one command header and no second protocol-status label. A live interactive terminal uses a dark, content-sized four-to-eight-row xterm; when its tool enters a terminal state, Farming immediately disables stale input and Stop controls, then refreshes the authoritative terminal detail before replacing that xterm with compact read-only output and exact exit metadata. If bounded refresh cannot observe the terminal outcome, the read-only evidence shows an explicit synchronization failure with a Retry action instead of remaining in a false running state. Raw output that contains only the same exit code or signal is omitted from the visual projection but remains available through exact copied tool detail. When the bottom live-activity row is present, the generic waiting placeholder is suppressed so the turn has one waiting signal. Later stream updates never overwrite an explicit per-tool or per-child disclosure choice, and opening the complete Process view keeps any already-open item reachable by opening its containing group. The top-level Process still folds when the Turn completes so the final result regains focus, while an explicitly opened child card remains open because it is a separate disclosure. Opening Process reveals the complete ACP-ordered evidence and only then auto-opens the latest streaming thought. Its summary and compact action rows stay on one ellipsized line, with the compact action row owning the localized provider-reported tool title and no duplicate protocol-status badge. Successful generated image or audio outputs are promoted from their tool entry to a default-visible result-media surface while their tool metadata remains reversible under the process disclosure. The version-locked Codex adapter converts `thread/read` image and local-image inputs into standard ACP image or resource-link blocks; Farming consumes those blocks directly and never reconstructs history images from rollout JSONL, while injected attachment paths and wrapper text stay out of the visible request. Mermaid code fences decode Markdown character references once before parsing, allowing protocol text such as `&lt;id&gt;` to render as the intended diagram source. A tool update containing ACP `diff` blocks is projected as a file-change result card without flattening away the protocol data: the collapsed card shows deduplicated paths and line totals, its first expansion lists the affected files, and each file can reveal the exact historical ACP patch on demand. The separate Review action captures only paths inside the Agent workspace instead of opening an unrelated whole-workspace change set; out-of-workspace patches remain inspectable inline. Tool details, raw input/output, compact contextual patches, terminals, and locations remain expandable. ACP child sessions remain nested under their parent tool entry; the preview can be opened in a focused dialog, a running child can be stopped independently, and child permissions or elicitation forms are answered through the parent Chat controls. Large details are omitted from the transcript page and fetched by tool-call id only when the user expands or copies that item. The ACP Chat view initially projects 20 turns and loads older turns in 20-turn pages as the user scrolls upward. ACP transcript refreshes follow session update signals from the shared state websocket and request only the changed suffix. Internal Codex context and heartbeat activity is hidden as a segment, while a visible automation notification remains an assistant message.

The current transcript presentation supersedes the compact-trail defaults described above. The authoritative Session plan is one view-attached translucent driver that updates in place and never appears as a chronological entry; its entries use plain ordered numbering rather than colored status dots. The driver follows the active appearance theme and remains visible only while at least one plan entry is incomplete, so a fully completed plan no longer obscures the finished answer or reserves transcript space even if the backend retains its last authoritative snapshot. Completed entries are de-emphasized, the current entry uses darker slightly heavier text, and pending entries remain neutral gray. Full commentary and admitted steer messages remain in ACP order and divide evidence into segments. Each segment renders one collapsed, dot-free text summary row for all of its reasoning and tool activity; opening that row still leaves every child reasoning/tool detail collapsed until the user opens it, and child rows also remain plain text without status dots. A reasoning-only segment is flattened directly into its ordered child entries instead of rendering `Reasoning > Reasoning`; each child uses a bounded first-line thought summary when available and keeps the full original detail behind its disclosure. Mixed reasoning/tool segments retain exact ACP order. Transcript disclosure chevrons keep their fixed layout slot but stay visually hidden until pointer hover, keyboard focus, or focus-within, while `aria-expanded` remains authoritative. ACP Process is visible by default, and neither reasoning nor terminal detail auto-expands. While the latest ACP turn is working, its live status occupies a separate normal-size row with a continuous loading treatment at the bottom of the turn instead of attaching to a preceding result or provider-specific message. If terminal outcome synchronization fails, the expanded row shows only the bounded retry notice; raw tool input stays out of that error surface while remaining available through explicit copy/detail paths.

Codex collaboration activity and child lifecycle are separate protocol facts. `collabAgentToolCall` and `subAgentActivity` describe what the parent attempted; an activity named `interrupted` is a pause request, not proof that the child ended in that state. After `session/load` or `session/resume`, the pinned Codex adapter therefore returns the parent transcript immediately and reconciles spawned descendants asynchronously with app-server `thread/list(ancestorThreadId)` plus bounded `thread/read(includeTurns)`. It emits a versioned full snapshot and ordered live deltas through Codex-specific `session_info_update` metadata. The Farming reducer checkpoints that state and advances the ordinary transcript revision, so retained and restored views converge without polling. UI lifecycle labels come only from the child thread's current status or authoritative final `turn/completed`; a completed turn is shown as completed, an interrupted turn as resumable paused, and activity records remain reversible evidence inside that child's own disclosure. Spawn-edge parent ids preserve nested child ownership. Review and Guardian threads that Codex intentionally excludes from the spawned-descendant lifecycle are not assigned an invented terminal state.

The ACP composer preserves the ordinary message-box behavior that does not depend on PTY input: drafts and history navigation, Enter/Shift+Enter and IME handling, file selection, pasted media previews, attachment removal, voice dictation, provider commands and skills, Goal/Plan request modes, queued follow-ups, interrupt, context-window usage when exact Codex data is available, and provider permission/configuration controls. Queued follow-ups stack above the Composer on the same visual surface. Before a queued item enters prompt or steer admission, the user can discard it or remove it back into the Composer for editing; Arrow Up recalls the newest queued item from the first input line. Recall preserves its original editable text, request mode, and native attachments, while a message whose admission has already started cannot be withdrawn through this edit action. The `+` menu contains attachment, Goal, and Plan actions, plus Sign out only when the Agent advertises ACP logout; provider commands remain searchable through `/`, while `$` opens the provider-advertised skill subset. Uploaded images or audio travel as native ACP content blocks only when the live Agent advertises that prompt capability. Otherwise Farming converts the upload into the same readable local-path context used by the existing text fallback, so an unsupported media type cannot be silently dropped. Text files remain embedded in the message.

Farming Code checkpoints Composer drafts, bounded input history, queued follow-ups, and unresolved submission cards in versioned browser-local storage under the stable Terminal or ACP Composer identity. React remains the authoritative runtime owner. The checkpoint excludes open menus, history cursors, uploads that have not reached a ready server path, and blob preview URLs. A restored in-flight submission becomes a visible failed item that requires explicit same-request-id reconciliation; page restoration never automatically replays an ambiguous Prompt or Steer. Corrupt, expired, or oversized checkpoints are ignored without blocking the Composer, and page hide performs a synchronous best-effort flush after the normal short debounce.

Structured Composer submission is request-idempotent. Both browser skins retain the same request id across a disconnect or explicit UNKNOWN response; Farming Code does the same after its bounded admission timeout. An ordinary Prompt sent while no turn is active goes directly through this admission path and does not first appear in the visible queued-message strip. The exact draft remains editable until a definite admission ACK; only that matching draft is then cleared, and a late ACK cannot clear newer input or steal focus. Before calling ACP, Farming persists a bounded sidecar record containing the request id and content hash. The provider's `onSubmitted` callback is the admission linearization point: Farming persists `accepted` before acknowledging the browser. A repeated id with the same hash joins or returns the committed result; a different hash is rejected. If provider ownership is possible but the accepted state cannot be proved, the record becomes UNKNOWN and Farming never automatically replays the Prompt or Steer.

For Codex, Farming maps the selected launch profile into the ACP adapter's `CODEX_CONFIG` and `INITIAL_AGENT_MODE`. Switching between Terminal and Chat therefore preserves model, reasoning effort, service tier, and the matching initial permission mode instead of silently reverting to adapter defaults.

Changing a Codex model in a live ACP session first lets the adapter choose a compatible reasoning fallback, then refreshes the adapter's model catalog and reapplies the standard config option. This keeps model-specific capabilities such as Fast mode aligned with the refreshed model metadata even when a long-lived session was opened before the provider or proxy updated that metadata. Related model and reasoning changes can be applied as one profile update. For model families that expose Sol, Terra, and Luna variants, the composer presents one continuous draggable surface for variant and ordinary reasoning selection, a click-operated red Ultra rocker that automatically pulls down when enabled, and a separate `Fast OFF` / `Fast ON` speed button. **Advanced** morphs back to the exact step-by-step reasoning, model, and speed controls without resetting the selected profile. ACP configuration writes are serialized per live session for every provider, repeat requests for an already-selected target are idempotent, and the returned config options must confirm the requested value. The browser applies one optimistic update while that transaction is pending and ignores older refreshes, then reconciles with the confirmed session snapshot or rolls back on failure. The Ultra and Fast positions remain stable while capabilities refresh; a control that the live session does not advertise stays visible, grey, and disabled instead of making the menu jump.

The same controls also update an idle native Codex Terminal instead of changing only its next launch profile. Farming applies the change through the CLI's interactive `/model` selection and non-interactive `/fast` toggle command. It waits for the actual model and reasoning menus, selects the advertised entries, and confirms the resulting footer before the Composer can submit another message; it does not guess at remote-render timing. Fast is different: it is one non-interactive toggle command, so later Terminal input is released as soon as that complete command is accepted by the PTY while confirmation continues outside the input queue. While a Terminal turn is active these controls stay disabled, because ordinary TUI input can be queued as task input instead of taking effect as an immediate configuration command. New Terminals receive an explicit `service_tier="default"` when Standard is selected, so a Fast value in the user's Codex config cannot make the runtime disagree with Farming's control. The launch profile is persisted after the live Terminal confirms the change, keeping a restarted Agent consistent without showing an unverified selection. These PTY commands are never injected into ACP, shell, Claude, OpenCode, Qoder, or other non-Codex Terminal sessions.

ACP boundaries remain explicit:

- The active binding object is ACP's in-process generation fence. `agentId` routes the live Farming runtime and the provider `sessionId` scopes protocol messages; every asynchronous completion and Agent-to-client request must still match the current open binding before it can reduce state, emit an update, or schedule a checkpoint. A base prompt reserves admission synchronously before the dirty-checkpoint write, so a second prompt cannot pass the same idle state. Cancellation during that admission window revokes the prompt before it reaches the provider. Detached or closed bindings cancel late permission/input requests and cannot become usable again.
- Base ACP has no concurrent prompt/steer operation. Every submitted Chat message first enters one per-Agent admission sequence and rechecks the exact current binding and Turn when it reaches the front. When the live Codex adapter advertises Farming's versioned steer extension, an active-Turn message is serialized with that Turn's other controls. A definite turn-end or non-steerable-turn rejection keeps the message in its original admission position, waits for that exact Turn to settle, and then starts the next prompt; a later message cannot overtake it, and an ambiguous transport failure is never replayed. A message admitted while cancellation is in progress likewise waits for the cancellation's proven terminal result. Interrupt targets the exact current Turn and may preempt messages that have not reached the provider. Providers without the capability retain the visible, discardable queued-follow-up behavior.
- The global Composer follow-up preference defaults to **Queue** and may be changed to **Steer**. During an active Turn, ordinary Enter uses that preference while Command/Ctrl+Enter reverses it for exactly one message. An idle Composer always starts a normal Prompt, and a provider that does not advertise Steer always uses Queue regardless of the preference.
- Each observed child Session has a binding-local control owner with its own generation and single-flight cancellation. Duplicate child stops join one provider request, parent cancellation also cancels every child still proven active, and an old binding's completion cannot mutate a replacement binding. Late child transcript notifications may still be reduced as evidence, but cannot reopen a child whose cancellation has already reached a terminal state.
- Goal and Plan are explicit composer request modes. ACP Chat sends Goal as a portable prompt until a provider negotiates a native protocol capability. Terminal uses each verified provider path: Claude receives `/goal <condition>`, Qoder receives `/goal set <condition>`, while OpenCode receives the portable Goal prompt because its TUI has no native Goal lifecycle. Provider session modes, model, reasoning, speed, and other runtime settings are still shown only when the Agent advertises the corresponding ACP mode or config option. A negotiated model, reasoning, speed, or permission-mode change requested during an active turn is accepted as the latest pending Session change, checkpointed, shown with a warning, and applied at the next idle boundary before another prompt can reach the provider. Mode applies before config; a later config failure rolls the mode back, and any failed deferred change remains a visible runtime error until a later successful setting change clears it.
- A context-window percentage needs both used and maximum tokens. Codex uses its exact provider-session token event when available; ACP providers that expose only cumulative usage get a token count instead.
- The composer accepts images and audio, but native blocks are capability-negotiated independently. Incoming embedded resources and resource links are rendered, while arbitrary outbound resource-link construction is not exposed as a composer control.
- Editing an old prompt with a repository checkpoint and truncating later turns is not part of base ACP. Farming does not present that optional client-side capability as protocol support.

An explicit `input_image` / `inputImage` tool-result block that an Agent sends into the conversation is promoted to the same default-visible result-media surface as generated media. Its tool metadata remains reversible under Process; ordinary ACP tool media without that explicit output marker remains in the tool detail.

## Permissions And Failure Behavior

`full` permission mode selects an advertised allow option automatically. `ask` selects an advertised reject option. The normal approval mode exposes the full pending ACP permission request and waits for an explicit response through the backend API.

ACP startup, initialization, history restoration, prompt, protocol, and adapter-exit failures are reported as runtime errors. If a Provider also emits the same failure as a final-answer message, the Transcript projection keeps the structured Process error as the single visible copy; a distinct partial answer remains visible. When an adapter transport exits unexpectedly, an explicit Reconnect action or the next explicitly submitted message may replace the dead binding through one single-flight recovery per Agent. Recovery checkpoints the dirty revision fence, proves the exact old process group has stopped, launches the same Provider Session with its original Workspace, Provider Home, additional-directory, and MCP scope, and reloads authoritative history before accepting another prompt. A prompt active at disconnect is completed as an error and is never replayed; only a new user action or a definitively failed Composer request may be submitted after recovery. If old-process cleanup is uncertain, recovery remains failed instead of risking a second live adapter. Bounded control requests fail with actionable timeouts; a normal long-running prompt is not assigned an artificial wall-clock timeout. Farming does not silently replace a requested ACP Agent with Terminal. Chat / Terminal switching is rejected while a turn is active. A new Terminal with no user input may start a fresh ACP session when provider history has not been materialized yet; after Terminal input, the switch requires the saved session to remain discoverable. After the turn is idle, the switch stops the old process and starts the requested runtime; if that startup fails, Farming immediately resumes the same provider session in the original runtime and reports the failed switch.

After bounded request, Workspace, Agent Home, owned-executable, and durable Create-intent validation, a new Chat Agent is registered and its connecting view may open before user-shell environment collection, ACP initialization, history loading, and provider capability negotiation complete. The registered Agent remains the authoritative lifecycle owner: duplicate Create requests with the same request id join that lifecycle, reconnect reads it from backend state, and startup failure resolves through that lifecycle rather than a second speculative launch. The connecting Composer accepts and preserves a draft, but submission remains disabled until the runtime is ready. Updating the recent-Workspace preference never gates Agent creation: each browser serializes its own background updates, while the backend atomically prepends each Workspace to current settings so concurrent browsers cannot overwrite one another with stale lists.

## Backend API

- `GET /api/agents/:agentId/acp-session` returns the normalized session and negotiated capabilities. Add `?includeEntries=0` for the lightweight controls/usage snapshot. Add `?includeUpdates=1` only for protocol debugging when the bounded raw ACP update stream is required.
- `GET /api/agents/:agentId/acp-transcript?maxTurns=N` returns the sanitized canonical entry-stream projection inside the versioned Agent/Session/runtime-epoch checkpoint envelope. A live reader adds `sinceRevision=R`; the backend returns a continuous delta only when it can prove the suffix, otherwise it returns `replace: true` with a full checkpoint.
- `GET /api/agents/:agentId/acp-media/:entryId/:mediaId` serves one explicitly negotiated, authenticated, immutable transcript image or audio payload whose content hash still matches the authoritative entry.
- `GET /api/agents/:agentId/acp-tool-details/:toolCallId` loads expandable tool detail and exact structured ACP patches on demand.
- `GET /api/agents/:agentId/acp-sessions` calls ACP session listing for the live provider connection.
- `PATCH /api/agents/:agentId/acp-session` changes one negotiated mode/config option, or accepts `configOptions` for an atomic model-and-reasoning profile change.
- `POST /api/agents/:agentId/acp-session/reconnect` replaces an unexpectedly exited adapter while preserving the exact Provider Session and recovery scope.
- `POST /api/agents/:agentId/acp-permission` answers a pending permission request.
- `POST /api/agents/:agentId/acp-elicitation` answers a pending form or URL elicitation.
- `POST /api/agents/:agentId/acp-session/authenticate` starts a negotiated authentication method, including managed terminal authentication.
- `POST /api/agents/:agentId/acp-session/logout` logs out only when the Agent advertises ACP logout.
- `POST /api/agents/:agentId/acp-session/fork` forks a session when advertised.
- `DELETE /api/agents/:agentId/acp-sessions/:sessionId` deletes a session when advertised.
- `POST /api/agents/:agentId/acp-session/close` closes the current session when advertised.
- `POST /api/agents/:agentId/acp-terminals/:terminalId/input|resize|kill` controls an ACP client terminal.
- `POST /api/agents/:agentId/acp-subagents/:sessionId/cancel` stops a known ACP child session without cancelling the parent session.
- WebSocket `start-agent` accepts `agentRuntimeMode: "acp"`, optional `acpHistoryMode: "load" | "resume"`, and standard `additionalDirectories` / `mcpServers` session inputs. `POST /api/control/agents` accepts the same ACP session inputs.
- `POST /api/workspaces/recent` atomically moves one validated Workspace to the front of recent-Workspace settings. It is an independent preference update and never determines whether an Agent Create succeeds.
- WebSocket `acp-permission-response` answers the same permission flow without HTTP.

Farming Code's Chat control selects ACP for Codex, Claude Code, and OpenCode. Switching between Chat and Terminal restarts the Agent runtime and resumes the same provider session; the replacement preserves an already-visible composer instead of unexpectedly applying the default collapsed-Terminal preference. The removed JSON CLI runtime is not a launch, resume, or transcript path.

Fresh OpenCode Terminals pre-create an exact provider session through one bounded ACP process before native Terminal launch. Fresh and forked Codex Terminals launch immediately with a temporary correlation id and keep user-owned metadata on the stable Farming session record, including across native-host recovery. Once the rendered TUI reaches its ordinary idle composer, Farming serializes one internal `/status` command ahead of later user input and strictly extracts the UUID from the structured status block. Selection pages, active turns, menus, an existing unsubmitted user draft, arbitrary terminal text, stale runtime epochs, and identities already claimed by another live Agent cannot commit a binding. An uncertain PTY write is reconciled from the rendered response and is never replayed; a late valid status response may still finish the same runtime-epoch attempt. Failure leaves the identity temporary and never falls back to History discovery. The confirmed provider id is attached atomically to the same Farming record for later Chat/Terminal resume and Fork. Farming-owned `/status` traffic does not set the user-input fence. Submitted user input is still fenced before awaiting its PTY response; after that fence, Chat, permission restart, and Fork require the exact provider id. A native-host runtime rotation also aborts and resumes the old host while such a used Terminal remains temporary, because relaunching `codex` would silently replace its conversation.

Terminal mode continues to use `NativeSessionEngine`. ACP is a structured runtime selected for a newly launched or restarted Agent; it does not duplicate a Terminal process.
