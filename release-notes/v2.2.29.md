# Farming v2.2.29

[简体中文](./v2.2.29.zh_cn.md)

Milestone codename: **BROWSER**

This release turns Browser Resources into a maintainable shared browser capability. Farming now delegates browser operations to an exact, managed `agent-browser` runtime, gives people and Agents the same visible page, and avoids bundling Chromium or managing externally owned browsers and containers.

## Highlights

- Browser Resources now use one version-locked `agent-browser` implementation for local and external-CDP sources. Farming prepares and verifies that runtime automatically during installation or update, without bundling Chromium, Playwright, Puppeteer, WebDriver, or a second raw-CDP automation path.
- **Plugins → Browser** is the single place to enable the capability and choose its source. Users can select a discovered Chromium-based browser or an explicitly configured loopback CDP endpoint; switching sources validates the new choice and stops owned Browser Resources before committing it.
- With a local source, a Project shares one Farming-owned browser process, isolated profile, login state, and `agent-browser` Session across its Browser Resources. With external CDP, the Project shares an `agent-browser` connection to the externally owned browser, profile, and login state. In both cases, each Resource is a separately visible tab that Farming owns and can open, switch, navigate, or close without a destructive-delete prompt.
- The shared Viewer carries the runtime's JPEG stream and maps pointer, keyboard, wheel, navigation, and viewport input back to the same Session used by the Agent. Browser rows, Viewer generations, actions, tabs, and stop/drain behavior now have explicit lifecycle ownership and bounded failure states.
- Agents discover Browser availability through `farming capabilities` and use the progressively disclosed `farming browser` workflow. The supported surface covers navigation and waits, DOM interaction, inspection and JavaScript, console/error/network evidence, cookies/storage, frames/dialogs, and Project-scoped uploads and downloads. Browser MCP remains an explicit opt-in instead of being mounted automatically.
- Farming can connect to a browser running in Docker through a user-managed loopback CDP endpoint. Farming intentionally does not access the Docker socket, choose or pull images, manage containers, or own the external browser lifecycle.

## Plugins and Agent visibility

- A dedicated Plugins view is available from the top-left puzzle button and the welcome page.
- Farming's built-in capabilities appear first. Detected Skills, plugins, commands, and other extension types are grouped by Agent in independently collapsible type sections with fixed-height cards, so large installations remain scannable without distorting the page.
- Empty Browser UI is hidden, and plugin cards stay compact until the user opens their details.

## Runtime and reliability

- Codex CLI, Claude Code CLI, and `agent-browser` are startup dependencies rather than bundled package dependencies. Installation and update preparation download, verify, stage, and atomically activate exact artifacts before the restart window; a fresh Server revalidates them before opening its port and prunes obsolete cache entries only after a healthy start.
- Large ACP transcripts use bounded, revision-aware loading, while collaboration Agents and their process evidence stay collapsed and unmounted until opened. Read-only transcript recovery may retry bounded transport failures without replaying prompts or terminal input.
- Farming Server restart and update paths are crash-only and identity-fenced. Browser sessions, native PTY hosts, update rollback, terminal attachment, and reconnect UI received additional ownership and recovery checks.
